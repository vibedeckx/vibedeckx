# 存储分层决策模型：一份新数据该放哪

> 通用参考文档。2026-08-06。
>
> 适用对象：**任何有一部分实例跑在你不运维的机器上的软件**——桌面应用、CLI 工具、
> 移动端、本地 agent、on-prem 部署、以及 server/worker 混合架构。
>
> 本文只回答一个问题：新增一份持久化数据时，它该以什么形态、放在哪一层。
> 具体到 vibedeckx 的经验素材见 [`state-storage-and-migration.md`](./state-storage-and-migration.md)，
> 落地计划见 [`plans/2026-08-06-session-entries-to-files.md`](./plans/2026-08-06-session-entries-to-files.md)。

## 1. 常见的问法是错的

这个决定通常被表述成「文件还是数据库」，并配上一组耳熟的论断：

> 文件灵活但要在代码里兼容旧格式，代码质量随时间下降；
> 数据库可以迁移到最新状态，代码只处理最新状态。

机制描述是对的：**数据库迁移是一次性、eager、全量的转换；文件容忍是惰性、逐次读、
永久的转换。** 前者把复杂度压缩到只跑一次的地方，后者摊到每个读点并且永远摊着。

但「代码只处理最新状态」有个前提——**你能保证所有实例都迁移过了**。
一旦有实例跑在你不控制的机器上，这个前提就没了，而整个论断随之失效。

更重要的是，这个问法把**介质**当成了决策变量。真正的决策变量是别的东西。

## 2. 核心模型：还剩几条退路

设想一个**加法改不动**的变更：改主键、改列类型、给已有列加 NOT NULL、
把一列拆成两列、重划整个结构。这类变更在关系型存储里都要求**重建表**
（建新表 → 拷贝 → 删旧表 → 改名）。

问题不是「你用了什么存储」，而是**这一刻你手上还剩几张牌**。牌面由两个维度决定：

|  | **你控制部署** | **用户控制部署** |
|---|---|---|
| **数据可重建**（派生 / 缓存 / 日志 / 索引） | `migrate` ✓ | **`discard` ✓** |
| **数据不可重建**（用户的源真相） | `migrate` ✓ | **两张牌都没有** ⚠ |

三种策略各自的可用条件：

| 策略 | 做法 | 可用条件 | 代价 |
|---|---|---|---|
| **migrate** | 把旧数据改成新形状 | **你控制部署**（能保证所有实例都转换过） | 不可回滚；写错就是全表 |
| **discard** | 不要旧数据了，从零重建 | **数据可重建** | 丢失只存在于该存储里的那部分状态 |
| **tolerate** | 读的时候认旧形状 | 总是可用 | 永久成本；必须收敛到单一边界 |

### 2.1 三个格子的解

**「你控制部署」整列**：随便改。eager 全量转换，改完所有实例都是新形状，
代码可以只处理最新状态。这一列不需要本文的任何技巧。

**「用户控制部署 + 可重建」**：改不动就换代——旧存储整个作废，新的从零建起，
重建逻辑（新装用户本来就要跑的那套）把数据灌回来。见 §3。

**「用户控制部署 + 不可重建」**：被困。
- `migrate`？要在你不运维的机器上做不可回滚的重建表。写错了，用户数据没了，
  版本回退也救不回来。
- `discard`？数据不可重建，扔了就是扔了。

### 2.2 被困格子的解：让它没有 schema

这一格的出路不是「换个更好的数据库」，而是**取消 schema 这个概念**：

```
append-only 文件 + 读端容忍
  ├─ 不需要 migrate ── 没有表结构可以重建
  ├─ 不需要 discard ── 数据从来不用作废
  └─ 格式演进由读端消化：新字段可选,老记录读出来缺字段而已
```

关键是**故障粒度**：迁移写错 → 整张表毁了，不可回滚；容忍写错 → 一条记录读出来是错的，
能修能回滚。在你够不着的机器上，这个差别是决定性的。

> **常见误解**：「文件比数据库更适合客户端」。
> 不是。**文件只是「没有 schema」这个属性的一种实现**，而「没有 schema」才是被困格子
> 真正需要的东西。如果你的运行时有别的方式做到无 schema 演进，同样成立。

### 2.3 这条因果链常被写短

一个高频错误是直接写成「用户控制部署 ⇒ 用文件」。**这条推不出来。**

「用户控制部署」直接推出的是三条**纪律**，不是一种存储：

1. **加法约束**：只做 `ADD COLUMN` / `CREATE` / `DROP`，老代码忽略新字段、新代码容忍缺失
2. **永久容忍**：兼容层不能当「待清理项」，它没有清理的那一天
3. **无法运维**：不能要求用户跑 SQL、跑 runbook，只能自愈

**数据库完全能满足这三条**（§5.2 有实证）。所以准确的因果是：

```
用户控制部署              → 加法约束 + 永久容忍 + 无法运维     ← 数据库做得到
用户控制部署 + 不可重建   → migrate 和 discard 同时不可用      ← 这才逼出无 schema
```

## 3. `discard` 的实现：文件名带代号

「可重建」这一格有个成本极低的做法，值得单独讲，因为它把 `discard`
从「迁移失败时的应急出口」变成**常态可选项**。

做法：**把存储的标识（文件名 / 目录名 / 库名）里嵌一个代号，代号是代码里的常量。**

```
v1.0 的代码:  open("state_5.db")
v1.1 的代码:  open("state_6.db")     ← 只改了一个字符串常量

用户升级到 v1.1:
  open("state_6.db") → 不存在 → 建空的 → 从头跑建表/重建 → 灌回数据
  state_5.db         → 代码里已无任何地方提到它 → 死文件,留着或下版删掉
```

**为「换代」写的代码是 0 行**：没有 5→6 的迁移脚本，没有读旧形状的分支，没有回滚预案。

### 3.1 它真正的价值不是「能删数据」

`DROP TABLE` 也能删。代号的价值在于**它把升级变成了全新安装**：

| | 固定标识 + 删表重建 | 代号 |
|---|---|---|
| 怎么知道该重建 | 读一个 schema 版本号 → 判断 → 走删除逻辑 | 存储不存在，运行时直接告诉你 |
| 代码路径 | 两条：新用户建库 / 老用户重建 | **一条**：不存在就建 |
| 要测的场景 | 「从 v0.3 升上来」「从 v0.7 升上来」…… | **只有全新安装**，而这条路径天天在测 |
| 用户降级 | 旧数据已被你删了，回不去 | 老版本打开老存储，原封不动 |

第三行是关键：**没有升级路径要测，因为压根不存在升级路径。**
一个用了两年的老用户和一个刚装完的新用户走的是同一条代码。

第四行在客户端场景尤其重要：**用户会降级**。原地迁移是一扇开在你够不着的机器上的
单向门；代号方案下新旧版本操作不同的存储，回滚就是回滚。
（前提是别急着删旧文件，留一个版本的宽限期。）

### 3.2 代号与迁移号是两层，别混

```
state_5.db
      ↑                 ← 代号(标识里):不连续。换 = 数据作废,重新开始
  内含 migrations 表      ← 迁移号(存储内):连续。升 = 数据保留,形状演进
```

日常绝大多数变更走迁移号。代号是**迁移号走不动时的逃生门**——
想改主键、重划结构、推翻整个模型时，与其写一个又险又不可逆的迁移，不如换代重来。

### 3.3 代号也是清「只扩不收」债的地方

被困在「只能加法」的存储里，久了必然长出平行字段：不敢改语义，于是并排加一个新的，
老的留着。这就是 expand → migrate → **contract 永远做不到**的状态。

这些债最后靠换代一次清零：新一代从零定义，只写新形状。
**能定期清债，反过来让你敢于在日常快速做加法。** 两者是配套的。

### 3.4 前提：只有可重建的数据能换代

换代前要确认，**只存在于该存储、且重建不出来的那部分状态足够小、丢了足够不心疼**。
典型的漏网之鱼是「用户后来做的操作」——归档标记、自定义名称、排序偏好、收藏。
这些通常不在源真相里，重建不出来。

量小可以接受；量大就该把那部分先挪到不换代的层去。

## 4. 另外两道门

①② 决定去哪一层。落地前还有两道独立的门。

### 4.1 形态可行性

无 schema 的追加式存储有两个硬前提：

- **追加写**，没有真正的就地更新需求。
  （注意甄别：「同一条记录被重写一次」如果只是**幂等重写**，
  append-only + last-wins 回放天然等价，不算就地更新。）
- **不需要跨记录查询**。只按主键整段读回可以；要跨记录聚合、过滤、join 就不行。

**如果被困格子里的数据又需要跨记录查询**，正确形态不是退回单一数据库，而是：

```
源真相 → 无 schema 文件(不迁移,不换代)
索引   → 可换代的派生库(全文索引/倒排/统计)
```

索引是派生的，随时能从源真相重建，所以它落在「可重建」那一格，享有 `discard` 退路。
**这是最常见的正确组合，也是很多系统实际长成的样子。**

### 4.2 优先级：增长率，不是当前大小

决策发生在**建表之前**，那时你不知道量会有多大，只知道它**跟着什么增长**：

| 跟着什么增长 | 紧迫性 |
|---|---|
| 每条消息 / 每行输出 / 每个事件 | **高**——几个月内会变成主体 |
| 每个会话 / 每次任务 | 中——盯着 |
| 每个用户 / 每项配置 | 无 |

> 增长率是**「停下来重新问一遍」的触发器，不是结论**。
> 它只说明这份数据值得单独想，不说明答案。

漏判几乎总是发生在这里：一张新表加进来时是 0 行、五个列、看上去毫无问题，
问题全部来自它跟着什么增长。

## 5. 实证

> 2026-08-05 / 08-06 实测三个真实系统。快照会随版本漂移，
> 重点看**策略分层**而非具体文件名。

### 5.1 三个系统的分层

| | 用户源真相 | 派生 / 缓存 / 日志 | 策略 |
|---|---|---|---|
| Claude Code | JSONL / Markdown 文件 | 文件 | 全部 tolerate（无核心数据库） |
| Codex | JSONL rollouts | SQLite ×4，文件名带代号 | 真相 tolerate；派生 migrate + discard |
| vibedeckx（worker） | **SQLite**（与派生同库） | 同一个库 | 全部 migrate |

前两家都把**用户源真相放在文件里、且不迁移**，把数据库限定在「丢了能重建」的范围内
——于是数据库可以随便换代。第三家把两者放进同一个库，所以每次 schema 变更
都要在用户机器上做不可回滚的迁移。

### 5.2 数据库确实能在版本倾斜下活着

Codex 的 `state_5.sqlite` 装在大量用户机器上，实测 **42 条迁移、跨 11 个日期、5 个月**：

- 全部落在 `ADD COLUMN` / `CREATE TABLE` / `CREATE INDEX` / `DROP TABLE`
- 其中 **5 条是 `DROP`**——他们真的删表，不像被困在源真相里的库那样只增不减
- 主表的 schema 尾部是 `ALTER TABLE ADD COLUMN` 追加的一长行，**证明从未重建过表**

**这证伪了「用户控制部署 ⇒ 必须用文件」。** 数据库能撑住，只要坚持加法，
并且在改不动时有换代这条退路。

### 5.3 换代 = 从零建库 + 从源真相重建

同一台机器上：

```
最早的 rollout JSONL          2025-12-19
state_5.sqlite 诞生           2026-02-27   ← 前 22 条迁移在同一秒安装(从零建起)
```

而 `state_5` 的主表里有 **1394 行、最早一条 2025-12-19**，其中 **452 行早于
数据库文件本身**——只可能来自扫 rollout JSONL 重建。库里还有一张单行的
`backfill_state`（`status` / `last_watermark` / `last_success_at`），
以及一列 `rollout_path` 直接存着回指源文件的指针。

**源真相横跨换代完好无损。** 这就是 §3.4 那个前提的实际样子。

### 5.4 换代不是无损的

同一张表里，`archived` / `name` / `nickname` 这类**用户后来的操作**在源文件里没有，
重建不出来。他们接受了这个代价，因为量小——丢一个归档标记，和丢一场对话，
不是一个量级。

### 5.5 成本可以有多集中

vibedeckx worker 的实测（`dbstat` 分表统计，423.6 MiB）：

```
会话记录表 + 其索引     420.1 MiB   =  99%      284,498 行
其余全部                 ≈ 3.5 MiB              ≈ 5,800 行
```

**迁移痛苦的 99% 由一张表贡献。** 这也说明分层的收益高度集中：
把那一张挪走，剩下的关系型层退回「一个下午能写完的 migration script」那个量级。

## 6. 收敛比介质更决定代码质量

最后一条，也是最容易被介质之争掩盖的一条。

数据库同样积压兼容债，只是从 `.ts` 挪进了 `.sql`：删不掉的旧列（删了要重建表、
老库读不了）和「代码里留着旧格式分支」是同一种债。

真正决定质量的是：

> **旧格式处理是收在一个边界后面，还是散在每个读点上。**
>
> 一个 `parseEntry()` 里包含五代格式分支是好代码；
> 五代分支散在二十个调用点是烂代码。
>
> **这个变量与文件/数据库的选择基本正交。**

所以做完分层还要做收敛：把 N 类消费者各自处理旧形状，改成全部走同一个解析 / 投影函数。
剩下的条件判断应当都是业务门禁，而不是格式兼容。

判断兼容代码有没有终点，看**信息是否完整**：

- 旧数据自身可读出、可转换 → **有终点**。写搬迁，收敛后删兼容分支。
- 无法自证（原始上下文已消失）→ **没有终点**。承认它是永久支持状态，别当待办。

**不取决于它是不是「老数据」。**

## 7. 速查

```
新增一份持久化数据
 │
 ├─ 谁控制这些实例的部署?
 │   ├─ 你 ────────────────────→ 数据库,正常迁移。本文其余部分不适用
 │   └─ 用户 ↓
 │
 ├─ 这份数据丢了能重建吗?
 │   ├─ 能 ────────────────────→ 数据库 + 标识带代号,并写明"允许丢弃"
 │   │                            (§3.4:确认只存在于此的用户操作足够小)
 │   └─ 不能 ↓
 │
 ├─ 追加写? 且不需要跨记录查询?
 │   ├─ 是 ────────────────────→ append-only 文件,读端容忍,永不迁移永不换代
 │   └─ 需要查询 ──────────────→ 文件(源真相) + 可换代的索引库(派生)
 │
 └─ 何时动手?
     跟着每条消息/每次输出增长 → 现在
     跟着会话/任务增长          → 盯着
     跟着用户/配置增长          → 不用管
```

配套纪律，做完分层别忘：

- **旧格式处理收敛到单一边界**（§6），否则质量债按读点数量增长
- **加法优先**：新增字段/表可以随时做；重建表之前先问「这个存储能不能换代」
- **代号是声明**：标识里有代号 = 允许丢弃；没有 = 永不丢弃。让命名本身带上策略，
  比写在文档里更难被后来者误读

## 8. 适用边界

本模型的假设，不成立时结论会变：

- **假设存在「你够不着的实例」。** 纯服务端系统直接走 migrate，不需要这套。
- **假设旧版本会长期存在。** 如果能强制升级（且真的能），格局回到「你控制部署」那一列。
- **假设存储层的非加法变更需要重建。** 有真正在线 DDL 的数据库（如 Postgres 改列、
  加约束大多不重建表）会显著削弱换代的必要性——这也是为什么服务端那一列不需要代号。
- **不涉及一致性与并发。** 跨记录事务、多进程并发写这些需求会直接否掉文件方案，
  与本文的分层判断无关，需单独评估。
