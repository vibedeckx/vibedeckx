---
title: Connect a machine
description: Run agent sessions on your own hardware from vibedeckx.dev.
---

Agents run on machines you connect. The machine dials out to the Vibedeckx server, so it needs no open ports or public address.

In **Settings → Remote Servers**, add a server for the machine and open its connect token. The dialog shows two commands to copy and run on that machine.

## Install as a service

This is the one to use for a machine that should stay connected. It works on Linux, macOS and Windows; on Windows, run it from Command Prompt or PowerShell (no administrator rights needed):

```bash
npx vibedeckx@latest connect install --connect-to https://vibedeckx.dev --token <token>
```

It installs the worker as a service of your user: **systemd** on Linux, **launchd** on macOS, a **Task Scheduler** task on Windows. The worker then:

- starts when the machine boots (macOS and Windows: when you log in),
- restarts by itself if it crashes or is killed,
- keeps its own copy of Node and the worker, so later Node upgrades on the machine don't affect it.

The token is saved privately in the worker's data directory; the running worker never has it on its command line. To keep it out of your shell history as well, leave `--token` out and paste the token when prompted, or use `--token-file <path>`.

Running the same command again with a newer version upgrades the worker. The worker restarts only when something changed (a new version, token or server URL); otherwise the command reports that it is already up to date and leaves running sessions alone.

If the worker starts but cannot connect, for example because the token was revoked or belongs to another remote server, the command fails and prints the reason and how to fix it. The service stays installed and connects by itself once the token is fixed.

<Callout title="Linux: start at boot">
  systemd user services only start at boot when lingering is enabled for your user. `connect install` turns it on when it can; otherwise it prints the command, typically `sudo loginctl enable-linger $USER`.
</Callout>

<Callout title="macOS: after login">
  A launchd agent starts when you log in. For an unattended Mac, enable automatic login.
</Callout>

<Callout title="Windows: after sign-in">
  The task runs in the background, without a window, and starts when you sign in to Windows. For an unattended PC, enable automatic sign-in. If the worker crashes it is back within seconds; if its supervisor process is killed, the task brings both back within a minute. Requires Windows 10 version 1809 or later.
</Callout>

### Managing the worker

`connect install` also creates a `vibedeckx` command in `~/.local/bin` (`vibedeckx.cmd` in `%USERPROFILE%\.local\bin` on Windows) that runs the installed worker directly, without npx or a download. If that folder is not on your `PATH`, the installer tells you what to add.

| Command | What it does |
|---|---|
| `vibedeckx connect status` | Shows whether the worker is running and connected, and how to fix it if not |
| `vibedeckx connect stop` | Stops it until `start` or the next boot (macOS and Windows: the next login) |
| `vibedeckx connect start` | Starts it again |
| `vibedeckx connect restart` | Restarts it |
| `vibedeckx connect disable` | Stops it and keeps it off across reboots |
| `vibedeckx connect enable` | Turns auto-start back on and starts it |
| `vibedeckx connect uninstall` | Removes the service and the `vibedeckx` command; your data and token are kept |

`status` only looks at this machine. Add `--check-update` to also check for a newer version.

On macOS and Windows, a disabled worker does not start at all, so `start` and `restart` refuse until you run `enable`.

On Windows the worker's logs are in `%USERPROFILE%\.vibedeckx\logs`: `vibedeckx.log`, plus `supervise.log` and `worker-console.log` from the supervisor.

### Changing the token

If you rotate the token in **Settings → Remote Servers**, save the new one on the machine:

```bash
vibedeckx connect setup
```

It asks for the new token (press Enter to keep the current one). A running worker picks it up without a restart. While the token is invalid, `connect status` shows `auth-failed`.

If the machine should start serving a different remote server, run `connect setup --force` with that server's token, then `connect restart`. Without `--force` the worker refuses a token that belongs to another server and shows `blocked`.

## Run in the terminal only

The dialog's second command runs the worker until you close the terminal. It also works on systems where `connect install` is not available yet:

```bash
npx vibedeckx@latest connect --connect-to https://vibedeckx.dev --token <token>
```
