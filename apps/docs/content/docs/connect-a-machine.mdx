---
title: Connect a machine
description: Run agent sessions on your own hardware from vibedeckx.dev.
---

Agents run on machines you connect. The machine dials out to the Vibedeckx server, so it needs no open ports or public address.

In **Settings → Remote Servers**, add a server for the machine and open its connect token. The dialog shows two commands to copy and run on that machine.

## Install as a service

This is the one to use for a machine that should stay connected. It works on Linux, macOS and Windows; on Windows, run it from Command Prompt or PowerShell (no administrator rights needed):

```bash
npx vibedeckx@latest connect install --connect-to https://vibedeckx.dev --token <token>
```

It installs the worker as a service of your user: **systemd** on Linux, **launchd** on macOS, a **Task Scheduler** task on Windows. The worker then:

- starts when the machine boots (macOS and Windows: when you log in),
- restarts by itself if it crashes or is killed,
- keeps its own copy of Node and the worker, so later Node upgrades on the machine don't affect it.

The token is saved privately in the worker's data directory; the running worker never has it on its command line. To keep it out of your shell history as well, leave `--token` out and paste the token when prompted, or use `--token-file <path>`.

Running the same command again with a newer version upgrades the worker. The worker restarts only when something changed (a new version, token or server URL); otherwise the command reports that it is already up to date and leaves running sessions alone.

If the worker starts but cannot connect, for example because the token was revoked or belongs to another remote server, the command fails and prints the reason and how to fix it. The service stays installed and connects by itself once the token is fixed.

<Callout title="Linux: start at boot">
  systemd user services only start at boot when lingering is enabled for your user. `connect install` turns it on when it can; otherwise it prints the command, typically `sudo loginctl enable-linger $USER`.
</Callout>

<Callout title="macOS: after login">
  A launchd agent starts when you log in. For an unattended Mac, enable automatic login.
</Callout>

<Callout title="Windows: after sign-in">
  The task runs in the background, without a window, and starts when you sign in to Windows. For an unattended PC, enable automatic sign-in. If the worker crashes it is back within seconds; if its supervisor process is killed, the task brings both back within a minute. Requires Windows 10 version 1809 or later.
</Callout>

### Managing the worker

`connect install` also creates a `vibedeckx` command in `~/.local/bin` (`vibedeckx.cmd` in `%USERPROFILE%\.local\bin` on Windows) that runs the installed worker directly, without npx or a download. If that folder is not on your `PATH`, the installer tells you what to add.

| Command | What it does |
|---|---|
| `vibedeckx connect status` | Shows whether the worker is running and connected, and how to fix it if not |
| `vibedeckx connect stop` | Stops it until `start` or the next boot (macOS and Windows: the next login) |
| `vibedeckx connect start` | Starts it again |
| `vibedeckx connect restart` | Restarts it |
| `vibedeckx connect disable` | Stops it and keeps it off across reboots |
| `vibedeckx connect enable` | Turns auto-start back on and starts it |
| `vibedeckx connect uninstall` | Removes the service and the `vibedeckx` command; your data and token are kept |

`status` only looks at this machine. Add `--check-update` to also check for a newer version.

On macOS and Windows, a disabled worker does not start at all, so `start` and `restart` refuse until you run `enable`.

On Windows the worker's logs are in `%USERPROFILE%\.vibedeckx\logs`: `vibedeckx.log`, plus `supervise.log` and `worker-console.log` from the supervisor.

### Changing the token

If you rotate the token in **Settings → Remote Servers**, save the new one on the machine:

```bash
vibedeckx connect setup
```

It asks for the new token (press Enter to keep the current one). A running worker picks it up without a restart. While the token is invalid, `connect status` shows `auth-failed`.

If the machine should start serving a different remote server, run `connect setup --force` with that server's token, then `connect restart`. Without `--force` the worker refuses a token that belongs to another server and shows `blocked`.

## Run in Docker

For a machine without Node.js, or one where you'd rather keep the worker in a container, use the worker image `ghcr.io/vibedeckx/worker`. It contains Node, the worker, Claude Code and Codex. Only Docker is needed on the machine (Linux, x86-64).

Save the token in a directory of its own. The worker runs as user 1000 inside the container, so make the file readable by that user:

```bash
mkdir -p ~/vibedeckx-worker/secrets
cd ~/vibedeckx-worker
(umask 077 && printf '%s' '<token>' > secrets/connect-token)
sudo chown 1000 secrets/connect-token
```

Then start the worker:

```bash
docker run -d --name vibedeckx-worker --restart unless-stopped --init \
  -e VIBEDECKX_CONNECT_TO=https://vibedeckx.dev \
  -e VIBEDECKX_CONNECT_TOKEN_FILE=/run/vibedeckx-secrets/connect-token \
  -v "$PWD/secrets:/run/vibedeckx-secrets:ro" \
  -v vibedeckx-data:/data \
  -v vibedeckx-home:/home/node \
  -v vibedeckx-worktrees:/var/tmp/vibedeckx/worktrees \
  -v vibedeckx-projects:/projects \
  ghcr.io/vibedeckx/worker:latest
```

Docker restarts the worker if it crashes and starts it again when the machine boots. Everything worth keeping lives in volumes: the worker's data and identity (`/data`), agent logins and settings (`/home/node`), the worktrees it creates, and project checkouts (`/projects`).

Mount the token's directory, not the file itself: to change the token, overwrite `secrets/connect-token` and the running worker picks it up without a restart. The file now belongs to user 1000, so unless that is you, overwrite it with sudo; `tee` keeps its owner and permissions:

```bash
printf '%s' '<new token>' | sudo tee secrets/connect-token > /dev/null
```

If you prefer Compose, the repository has a ready-made [docker-compose.yml](https://github.com/vibedeckx/vibedeckx/blob/main/deploy/worker/docker-compose.yml) with the same settings.

### Keep projects in a host directory

To see and edit project checkouts from the host, mount a directory instead of the `vibedeckx-projects` volume. Create it first and give it to user 1000; a directory that Docker creates by itself belongs to root and the worker cannot write to it:

```bash
mkdir -p ~/vibedeckx-worker/projects
sudo chown 1000:1000 ~/vibedeckx-worker/projects
```

Then replace `-v vibedeckx-projects:/projects` with `-v "$PWD/projects:/projects"`.

### Let agents use the host's Docker

If your projects build or run containers, give the worker the host's Docker socket and CLI by adding these options to `docker run`:

```bash
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v /usr/bin/docker:/usr/local/bin/docker:ro \
  --group-add "$(stat -c %g /var/run/docker.sock)" \
```

`--group-add` lets user 1000 in the container use the socket.

<Callout type="warn" title="This gives agents root on the host">
  Whoever can use the Docker socket can start a container that mounts the host's whole filesystem. With these options, an agent session effectively has root access to the machine, not just to the container. Only add them on a machine you are prepared to hand over to agents.
</Callout>

### Sign in to the agents

A new container has no agent logins yet. Sign in once from the host; the login is kept in the `vibedeckx-home` volume:

```bash
docker exec -it vibedeckx-worker claude                      # then /login
docker exec -it vibedeckx-worker codex login --device-auth
```

### Managing the worker

Manage the container from the host:

| Command | What it does |
|---|---|
| `docker exec vibedeckx-worker vibedeckx connect status` | Shows whether the worker is running and connected |
| `docker stop vibedeckx-worker` | Stops it; it stays stopped across reboots until you start it |
| `docker start vibedeckx-worker` | Starts it again |
| `docker restart vibedeckx-worker` | Restarts it |
| `docker logs -f vibedeckx-worker` | Follows its output |

`connect stop`, `restart`, `disable` and the other service commands refuse to run inside the container and point you to these.

### Upgrading

Each Vibedeckx release publishes an image tagged with its version, and `latest`. To upgrade, pull the new image and recreate the container with the same `docker run` command; the volumes keep the worker's identity, logins and worktrees:

```bash
docker pull ghcr.io/vibedeckx/worker:latest
docker rm -f vibedeckx-worker
docker run ...   # the same command as above
```

The image includes the Claude Code and Codex versions current when it was built. To use a newer one before the next image, install it inside the container. It goes into the `vibedeckx-home` volume, so it survives upgrades and takes precedence over the built-in copy:

```bash
docker exec -it vibedeckx-worker sh -c 'curl -fsSL https://claude.ai/install.sh | bash'
docker exec -it vibedeckx-worker npm install -g @openai/codex@latest
docker restart vibedeckx-worker
```

Your projects will usually need more tools than the image has (language toolchains, build tools). Build your own image on top of it with `FROM ghcr.io/vibedeckx/worker:latest` and install them there.

## Run in the terminal only

The dialog's second command runs the worker until you close the terminal. It also works on systems where `connect install` is not available yet:

```bash
npx vibedeckx@latest connect --connect-to https://vibedeckx.dev --token <token>
```
